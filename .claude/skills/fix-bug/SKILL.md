# תיקון באג

הארגומנט: `$ARGUMENTS` (מספר `BUG-NN` מ-`product-backlog/BUGS.md`, או תיאור של באג שנמצא כרגע).
הכלל הקבוע ב-`CLAUDE.md`: **כל תיקון באג שמופיע ב-`BUGS.md` מסתיים בעדכון הקובץ — גם אם לא ביקשו.** ה-skill הוא הרצף המדויק.

## 1. הבן והעתק
1. אם יש מספר — קרא את הרשומה ב-`product-backlog/BUGS.md` (חומרה, מיקום, שחזור, "נשאר פתוח"). בדוק אם הוא מתועד ב-`specs/`
   (`grep` על `BUG-NN` ועל ההתנהגות).
2. **תשחזר לפני שאתה מתקן.** כתוב **טסט רגרסיה** שמשחזר בדיוק את מסלול הכשל, **והרץ אותו וראה שהוא נכשל** (אדום). טסט שלא נכשל
   בלי התיקון לא מוכיח כלום.
   - backend: Jest יחידה (`*.spec.ts` ליד הקוד) או e2e (`backend/test/`, מול `postgres-test`).
   - frontend: Jest ליד הקומפוננטה; באג התנהגות חוצה-מסכים — Playwright ב-`frontend/e2e/` (Desktop+Mobile).
   - שם הטסט/הערה בשורה אחת מתארים את הסימפטום המקורי ושם את `BUG-NN`.
3. אם אי אפשר לשחזר אוטומטית (למשל native על מכשיר, או תלוי בסודות/שירות חיצוני) — אמור זאת במפורש; זה **תיקון חלקי** (סעיף 4).

## 2. תקן
- שינוי מינימלי שסוגר את הבאג. לא "משפרים בדרך" דברים אחרים.
- סביבות: טסטים רק מול `postgres-test`; לעולם לא production, ולא `localhost:5005`. שינוי סכמה → `npm run migrate:new --prefix backend -- <name>` ואז `npm run migrate:sync --prefix backend`
  (פיתוח+בדיקות); ל-production — **רק נוה, באישור מפורש** (עצור ודווח).
- כללי הפרויקט חלים על הקוד שנוגעים בו (`TEAM.md` → Definition of done): מחרוזות ב-`Strings`, `trackEvent` על כל לחיץ חדש, web+native
  מסונכרנים, וכו'.

## 3. אמת
- הטסט החדש עובר (ירוק). הסוויטה הרלוונטית עוברת: `npm test --prefix backend` / `npm test --prefix frontend` / `npx tsc --noEmit -p .` מ-`frontend/`
  (אפס שגיאות **חדשות**; יש 4 ידועות שאינן קשורות), ו-e2e רלוונטי אם נגעת בזרימה.
- אם בדקת משהו ש"לא ניתן לאמת" — כתוב מה בדיוק לא נבדק.

## 4. עדכון `product-backlog/BUGS.md` — מדויק, כל השלבים
**תיקון מלא** (אין יותר מה לתקן):
1. **מחק את הרשומה כולה** (לא `[x]`). באגים 🟢 נמוכים הם **שורות בטבלה** — מוחקים את השורה. לא ממספרים מחדש.
2. **טבלת הסיכום** (`## סיכום`): הפחת 1 מהחומרה של הבאג.
3. **שורת "הכי דחוף":** עדכן אם הבאג שתוקן היה מוזכר בה, ובחר את הדחוף הבא מבין הפתוחים. ובאותה פסקה — המשפט
   "מתוך N הבאגים המקוריים, M תוקנו ונמחקו…": העלה את M ב-1, ואם הבאג היה ברשימת "תוקנו חלקית ונשארו" — הסר את מספרו משם.
4. **טבלת האשכולות:** הסר את המספר מכל שורה שהוא מופיע בה; שורה שנשארה בלי מספרים — מחק.
5. **סעיף חומרה שהתרוקן** — החזר את משפט ה-placeholder כמו ב-🔴 ("אין כרגע באגים … פתוחים.").
6. `specs/`: אם באג מתועד שם (כולל "known bugs"/edge cases) — עדכן את הסעיף לסטטוס הנכון.

**תיקון חלקי:** הרשומה **נשארת, מקוצרת** למה שעוד פתוח, עם "**תוקן חלקית DD.MM.YYYY:** <מה נסגר>" ו-"**נשאר פתוח:** <מה>", ומוסיפים את
המספר לרשימת "תוקנו חלקית ונשארו" אם לא היה שם. ספירות הסיכום לא משתנות.

**באג חדש שנחשף (בתיקון או בדרך):** הוסף רשומה בחומרה הנכונה, עם המספר הבא. **המספר הבא = הגבוה ביותר שהיה אי פעם + 1** (רשומות נמחקות,
אז לא מספיק להסתכל בקובץ):
```bash
git log -p -- product-backlog/BUGS.md | grep -oE 'BUG-[0-9]+' | sort -t- -k2 -n -u | tail -1
```
פורמט הרשומה: `- [ ] **BUG-NN — כותרת** · ✅/📖 (אומת בפועל / מקריאת קוד) ` + שורות `מיקום`, `פירוט`, `שחזור` (באגים נמוכים — שורה בטבלה).
עדכן את טבלת הסיכום, ואת האשכולות אם הוא קשור לאחרים. אל תתקן אותו כחלק מהמשימה הנוכחית אלא אם התבקשת.

**`TASKS.md`:** תיקון מלא → העבר את שורת `BUG-NN` ב-`product-backlog/TASKS.md` ל-`Done` (`[x]`) או מחק אותה; באג חדש → הוסף לה שורה (`Next`/`Later`).
תיקון חלקי → עדכן את הכותרת/`⛔` בשורה. סיים ב-`npm run tasks:check` (נכשל אם `BUGS.md` ו-`TASKS.md` לא מסונכרנים).

תאריכים בפורמט `DD.MM.YYYY` (כמו בקובץ). אחרי העריכה קרא את `BUGS.md` שוב וודא: הספירות בטבלה = מספר הרשומות הפתוחות בפועל לכל חומרה.

## 5. דווח (בעברית, קצר)
באג, מה היה הסימפטום, איזה טסט רגרסיה נוסף ושהוא נכשל לפני התיקון ועבר אחריו, מה שונה בקוד, מה נבדק, מה עודכן ב-`BUGS.md`/`specs/`
(ובאיזו חומרה/ספירה), ומה **לא** נבדק או נשאר פתוח. אל תעשה `commit`/`push` אלא אם התבקשת.
