# UI-GUIDELINES

> תבנית חובה לכל UI בפרוייקט. קלוד קורא את הקובץ הזה **לפני** שהוא כותב מסך, קומפוננטה או תיקון עיצובי.
> אם משהו כאן מתנגש עם קוד קיים — הקובץ הזה מנצח, והקוד הקיים משתנה.

## 0. הכיוון

מוצק ומעשי: כרטיסים ברורים, טיפוגרפיה חזקה, צבע ממוקד. RTL עברית.
Rubik לכותרות ולאלמנטי UI, Heebo לטקסט גוף. אקסנט אחד לכל האפליקציה.

## 1. ארבעת החוקים

1. **אין צבע, גופן, ריווח או רדיוס בקומפוננטה.** הכל מ-`useTheme()` ומ-`src/design/tokens.ts`.
   אפס גרדיאנטים, אפס `boxShadow` צבעוני, אפס hex בתוך `sx`.
2. **קלט אחד לכל האפליקציה.** כל שדה עובר דרך `<Field>`. אין `TextField` ישיר, אין `inputSx` מקומי.
3. **רשת קבועה.** כל מסך עטוף ב-`<Page>`, תוכן ברשת `<Grid columns={n}>`. פיצ׳ר חדש נכנס כתא — לא משנה רוחב ולא מזיז כותרת.
4. **היררכיה אחת.** כפתור `primary` אחד לכל מסך. כל השאר `secondary` / `ghost`.

## 2. ספריית הבסיס — `src/components/ui`

| קומפוננטה | תפקיד | מחליף |
|---|---|---|
| `Button` | primary / secondary / ghost / danger, גדלים sm / md | כל `MuiButton` עם `sx` |
| `Field` | text, email, password, number, date, textarea, select | כל `TextField` + תווית ידנית |
| `Card` | כרטיס יחיד, אופציונלי `placeholder` | `Card`+`CardContent` עם `sx` |
| `Badge` / `StatusDot` | מצב סמנטי (success / warning / danger / neutral / accent) | תגי מצב מקודדים, אימוג׳י |
| `Segmented` | בחירה בלעדית מ-2-4 אפשרויות | `Tabs`, `ToggleButtonGroup`, chips נבחרים |
| `Page` / `PageHeader` / `Grid` | מבנה מסך | `Box` עם `maxWidth` מקומי |
| `Icon` | אייקון קטן שמלווה טקסט/badge/כפתור | אימוג׳י כאייקון, SVG מקומי אד-הוק |

**להוסיף קומפוננטה שביעית רק אחרי שברור שאי אפשר להרכיב אותה מהשש.** קומפוננטה חדשה נכנסת ל-`ui/`, לא ל-`features/`.

## 3. טוקנים

`src/design/tokens.ts` — ניטרלים, שמונה סכימות אקסנט (blue / cyan / teal / green / amber / rose / purple / graphite) בכל מצב, ארבעה טונים סמנטיים, סקאלת טיפוגרפיה בת 9 מדרגות, ריווח 4pt, רדיוס 6/8/12/999, שלושה גדלי אייקון, שני צלים.

**מצב ספרינט לא בוחר צבע.** `sprintTone` ממפה `active → success`, `upcoming → warning`, `closed → neutral`.

## 4. ערכת נושא והעדפות משתמש

`AppThemeProvider` עוטף את האפליקציה פעם אחת בשורש. הוא מחזיק שלוש העדפות שנשמרות לכל משתמש:
`mode` (light / dark / system), `scheme` (סכימת אקסנט), `density` (compact / regular).

- קומפוננטה קוראת `useTheme()`. **אין prop `theme` שמועבר ידנית**, ואין `isDark` בתוך קומפוננטה.
- מסך ההעדפות: `features/settings/components/appearance-card.tsx`.
- ב-web, `createMuiTheme(theme)` מזרים את אותם טוקנים ל-MUI, כדי שגם קומפוננטת MUI לא-עטופה תיראה נכון.

## 5. RTL

- `dir="rtl"` פעם אחת בשורש. אחר כך `flexDirection: 'row'` רגיל — **לא** `row-reverse` בכל Box.
- מאפיינים לוגיים בלבד: `paddingInlineStart`, `marginInline`, `borderInlineEnd`, `textAlign: 'start'`.
- מספרים, תאריכים ומזהים באנגלית נשארים LTR — לעטוף ב-`<bdi>`.

## 6. תנועה

`transition` על hover / focus / press בלבד, `0.15s ease`.
**אין** `Grow`, `Fade`, `Collapse` על טעינת מסך, ואין `animation: pulse`.

## 7. מה אסור — checklist לפני כל commit של UI

- [ ] נבדק בפועל ברוחב טלפון (~375px, ראה סעיף 11) — אין גלילה אופקית, אין טקסט או כפתור חתוך/דחוס
- [ ] אין hex, `rgba(`, `linear-gradient` או `fontFamily` בשום קובץ מחוץ ל-`src/design/`
- [ ] אין `TextField`, `MuiButton` או `Card` מיובאים ישירות בקובץ תחת `features/`
- [ ] אין `row-reverse`, `marginLeft`, `paddingRight`, `textAlign: 'right'`
- [ ] אין אימוג׳י בכותרת, בתווית או בתג
- [ ] אייקונים (אם יש) רק מ-`Icon` עם `name` מהרשימה המורשית ב-`components/ui/icon.tsx` — לא אימוג׳י ולא SVG מקומי
- [ ] אין יותר מכפתור `primary` אחד במסך
- [ ] אין `Grow` / `Fade` סביב תוכן מסך
- [ ] font-size שנבחר קיים ב-`type`; ריווח שנבחר קיים ב-`space`
- [ ] המסך עטוף ב-`<Page>` ומספר הטורים ב-`<Grid>` קבוע

## 8. סדר עבודה על מסך חדש

1. `<Page>` + `<PageHeader title subtitle action>`.
2. להחליט מספר טורים ולהצהיר `<Grid columns={n}>`.
3. להרכיב מ-`Card` / `Field` / `Badge` / `Segmented` בלבד.
4. לעבור על ה-checklist בסעיף 7.
5. משהו לא מתאים? לעדכן טוקן או קומפוננטה ב-`ui/` — לא לעקוף מקומית.
6. לבדוק בפועל ברוחב טלפון (~375px, סעיף 11) — לא רק ברוחב desktop.

## 9. Native

הטוקנים משותפים ל-web ול-native. `ui/` ב-web בנוי על MUI; מקבילה native נכתבת כ-`*.native.tsx`
באותה תיקייה עם **אותו API בדיוק** ואותם טוקנים. מטרות נגיעה ב-native: `layout.minTouchTarget` = 44.

## 10. אייקונים

`Icon` הוא מקור האמת היחיד לאייקון — `components/ui/icon.tsx` (web, `lucide-react`) ו-
`components/ui/icon.native.tsx` (native, `lucide-react-native`), אותו API, אותה רשימת `IconName`.

- אין ייבוא ישיר של `lucide-react` / `lucide-react-native` תחת `features/` — רק דרך `<Icon name=... />`.
- גודל וטון רק דרך ה-props (`size`, `tone`) שמומרים לטוקנים ב-`iconSize`/`color`. אין `size={17}` חופשי.
- אייקון **מלווה** טקסט קיים (בכפתור, בתג) — הוא לא הופך להיות התווית הנגישה היחידה, אלא אם מדובר
  בפקד ייעודי עם `label`/`accessibilityLabel` (מחוץ לתחום הנוכחי — כרגע כל שימוש הוא אייקון+טקסט).
- להוסיף שם חדש ל-`IconName`/`REGISTRY` רק כשיש שימוש אמיתי — לא לייבא את כל ספריית lucide.

## 11. מובייל (חובה, כל פיצ׳ר)

**כל מסך או קומפוננטה חדשה נבדקים בפועל ברוחב טלפון (~375px) לפני שהמשימה נחשבת גמורה** — לא מספיק
שזה נראה טוב ברוחב desktop. סיבה: `<Page>`/`<Grid>`/`<PageHeader>` נבנו ראשונים בלי בדיקת מובייל,
ותוצאה הייתה לוח KEEP/IMPROVE ברוחב טלפון שנדחס לשני טורים בני ~150px כל אחד.

- ברייקפוינטים: משתמשים ב-`xs`/`sm` הסטנדרטיים של MUI בתוך `sx` (`{ xs: ..., sm: ... }`) — **לא**
  ממציאים טוקן breakpoint נפרד. זה כבר הדפוס הקיים (`comment-filter-bar-web.tsx`, `settings.tsx`).
- `<Grid columns={n}>` יורד אוטומטית לטור יחיד מתחת ל-`sm` (מובנה ברכיב). אל תעקפו את זה עם
  `gridTemplateColumns` מקומי קבוע.
- כל שורה אופקית (כותרת+פעולה, שורת כפתורים, פס סינון) מקבלת `flexWrap: 'wrap'`, ולתא הטקסט
  הגדל (title/label) — `minWidth: 0`, אחרת הוא דוחף רכיבים אחרים מחוץ למסך במקום להתכווץ.
- אין `minWidth` קבוע גדול (`Select`, `TextField` וכו') בתוך שורה שלא עוברת ל-`flexDirection: 'column'`
  ב-`xs`.
- בדיקה בפועל: Chrome DevTools → device toolbar ברוחב 375px, או resize חלון לרוחב דומה — לא הערכה
  מהעין בלבד.
- **native: RN flexbox לא web.** ברירת המחדל של `flexShrink` ב-React Native היא `0` (לא `1` כמו ב-CSS
  web) — בלי `flexWrap`+`flexShrink:1` מפורש על כל איבר, שורה שלא נכנסת **נגלשת מחוץ למסך** במקום
  להידחס. וב-native "מסך צר" הוא לא תרחיש-קצה — האפליקציה תמיד רצה ברוחב טלפון, אין desktop-width
  שבו זה "בסדר".
- **שורת מידע + אשכול פעולות (label + 3+ badge/כפתור): לא `flexWrap` על שורה אחת — שני שורות מכוונות.**
  `team-member-row.tsx` (web ו-native) היה בדיוק המקרה הזה: שם + עד 4 badge/כפתור (תפקיד, מנהל, ערוך,
  הסר) בשורה אחת עם `justifyContent:'space-between'`+`flexWrap`. גם אחרי הוספת ה-`flexWrap` זה עדיין
  *נראה* דחוס — כי נקודת השבירה תלויה באורך השם וב-locale, ומשתנה בין משתמש למשתמש; לפעמים הכל "נכנס"
  טכנית אבל צפוף מדי, לפעמים זה נשבר באמצע אשכול הבאדג'ים במקום לפני. הפתרון הנכון היה לא flexWrap
  נוסף — זה **פירוק ל-2 שורות קבועות מראש**: שורה 1 = הישות עצמה (שם/כותרת + badge סטטוס יחיד לכל
  היותר), שורה 2 = כל שאר ה-badge-ים והכפתורים, כל אחת ב-`flexWrap` משלה בתוך עצמה. זה עקבי בכל רוחב
  ולא תלוי בתוכן. **כלל אצבע:** אם יש יותר מ-2 badge/כפתור בצד השני של שורה מול תווית — אל תסמכו על
  `flexWrap` להחליט מתי לשבור; שברו מראש לשתי שורות.
- **אין למזג שני badge ממשמעות שונה (תפקיד מקצועי מול הרשאה) לצ'יפ אחד, גם אם זה "חוסך מקום".**
  ב-`team-member-row.tsx` נוסה מיזוג `"תפקיד • מנהל"` לתוך badge אחד כדי לצמצם צפיפות — אבל אחרי
  שהשורה כבר פורקה ל-2 שורות מכוונות (הכלל הקודם), הצפיפות כבר לא הייתה בעיה אמיתית, וה-badge הממוזג
  רק *נראה מוזר*: תפקיד מקצועי ("ראש צוות") והרשאת-מערכת ("מנהל") הן שתי עובדות שונות, ולערבב אותן
  לטקסט אחד באותו צבע/משקל נראה כמו תפקיד מומצא אחד ולא שתי עובדות ברורות. **תוקן בחזרה** לשני badge
  נפרדים (תפקיד ב-accent, "מנהל" ב-neutral). **כלל אצבע:** לפני שממזגים שני badge לחיסכון-מקום —
  לוודא קודם שיש בעיית-מקום אמיתית (בדקו את הכלל הקודם קודם), ולזכור ש-badge-ים ממשמעויות שונות
  (job role / permission / status) צריכים סגנון חזותי נבדל, לא רק טקסט משורשר.

## 12. פאנלים מרובי-סעיפים (הגדרות / ניהול)

`team-settings-panel.tsx` (web+native) עבר סבב עיצוב שני ב-2026-09-18 אחרי שנוה תיאר את הגרסה
הראשונה כ"על הפנים" — פונקציונלית תקינה, אבל קופסאות אפורות זהות ערוכות זו מתחת לזו בלי היררכיה.
הכללים כאן נגזרים מהתיקון בפועל (מוקאפ ב-`/design` → קוד אמיתי), לא תיאוריה:

- **תוכן ניתן-לעריכה: ברירת מחדל היא תצוגה, לא טופס פתוח.** שדה שרוב הזמן לא משתנה (שם צוות, פרטי
  פרופיל) מוצג כטקסט רגיל + כפתור `ghost` עם אייקון `edit` ("ערוך") שהופך את הבלוק לטופס. טופס
  שתמיד פתוח הוא גם עומס חזותי מיותר וגם סיכון ל"נגיעה בטעות" בשדה קריטי. ראו `isEditingDetails` +
  `handleStartEditDetails`/`handleCancelEditDetails` ב-`team-settings-panel.tsx`.
- **רשימת פריטים חוזרים (קטגוריות, חברים, וכו') לא נערמת בעמודה אחת בלי סוף.** גרסה ראשונה פתרה
  את "קיר הקופסאות" בקו-מפריד יחיד (`Box` אחד עם `borderBlockEnd` לכל שורה) — אבל עם הרבה פריטים
  (10+) זה עדיין נהיה ארוך ומתיש לגלול. **תיקון (2026-09-18, אותו יום, feedback נוסף):** כשיש מקום
  אופקי (web, `sm`+) — רשת 2 טורים (`display:'grid', gridTemplateColumns:{xs:'1fr', sm:'1fr 1fr'}`)
  של תאים ממוסגרים קטנים, לא רשימה מחוברת אחת; זה חוצה את האורך האנכי בערך בחצי. ב-native (רוחב
  טלפון קבוע) — `flexDirection:'row-reverse', flexWrap:'wrap'` עם כל תא ב-`flexBasis:'48%'`, ושם
  קטגוריה עם `numberOfLines={1}` כדי לספוג שמות ארוכים בתא הצר יותר. **כלל אצבע:** ≤4-5 פריטים ברוב
  המקרים לא שווה את המורכבות של רשת — רשימה חד-טורית עם `borderBlockEnd` מספיקה; יותר מזה ברוחב
  שמאפשר 2 טורים — עברו לרשת.
- **מצב לא-פעיל מסומן ב-`opacity` על כל השורה (~0.55), לא רק בצבע ה-switch.** כך אפשר לסרוק "מה
  פעיל עכשיו" במבט אחד בלי לקרוא כל toggle בנפרד.
- **תווית סעיף בתוך פאנל = `overline` (11px, 700, letterSpacing, `textMuted`, uppercase), לא
  `label`/`bodyStrong`.** ריווח נדיב (`space[6]`) *בין* סעיפים, ריווח צר (`space[2]`/`space[3]`)
  *בתוך* סעיף — זו ה"היררכיה" בפועל, לא רק גודל טקסט. פאנל עם כמה סעיפים שכולם נראים באותו משקל
  נקרא כמסה אחת בלי התחלה/סוף.
- **פקד סינון (filter) ≠ כפתור פעולה — מראה שונה בכוונה.** צ'יפ מעוגל-לגמרי (`radius.pill`), רקע
  `surface`, גבול `borderStrong` — לא `<Button variant="secondary">` הרגיל. ההבדל החזותי מתקשר
  "זה משנה מה מוצג" לעומת "זה מבצע פעולה".
- כל הכללים למעלה (סעיף 1: טוקנים בלבד; סעיף 11: מובייל) עדיין תקפים במלואם בתוך פאנל כזה — זה
  תוסף, לא חריגה.

## 13. גודל קובץ ופיצול עיצוב (חובה, כל קומפוננטה חדשה/מורחבת)

נקבע ב-2026-09-18 אחרי ש-`team-settings-panel.tsx` תפח ל-560-680 שורות עם עיצוב וסטייט מעורבבים
בקובץ אחד. היעד: **עד ~250 שורות לקובץ קומפוננטה** (web ו-native כאחד). כשקומפוננטה מתקרבת לגבול:

1. **עיצוב (`sx`/`style`) תמיד בקובץ נפרד — `<name>.styles.ts` באותה תיקייה**, לא inline בתוך
   ה-JSX. הקובץ מייצא פונקציית factory אחת, `getXStyles(t: AppTheme)`, שמחזירה אובייקט של ה-sx/style
   (web: `SxProps<Theme>` או פונקציה שמחזירה כזה לפרמטרים דינמיים כמו `isEnabled`/`checked`; native:
   `ViewStyle`/`TextStyle` באותו דפוס). הקומפוננטה קוראת `const s = getXStyles(t)` פעם אחת ומשתמשת
   ב-`s.thing` / `s.thing(param)`. כך שגלילה על קובץ קומפוננטה מראה מבנה ולוגיקה, לא בלוקי `sx`.
   דוגמה: `team-list-web/team-settings-panel.styles.ts` + `team-list-native/team-settings-panel.styles.ts`.
2. **JSX ארוך מתפצל לקומפוננטות-משנה פרזנטציוניות** (מקבלות props, בלי fetch/state עצמאי) בקבצים
   נפרדים באותה תיקייה. דוגמה: `team-details-section.tsx`, `category-list-section.tsx`
   (ו-`category-cell.tsx` ל-native, לפריט הכי-פנימי ברשת).
3. **סטייט+קריאות API שמתפרסים על הרבה handlers עוברים ל-custom hook** משלהם
   (`use-<name>.ts`) — הקומפוננטה הראשית (orchestrator) נשארת כמעט טהורה: קוראת ל-hook, מעבירה את
   השדות שהוא מחזיר כ-props לקומפוננטות-המשנה. אם הלוגיקה זהה לגמרי בין web ל-native (כמו כאן —
   אין בה קוד תלוי-פלטפורמה), ה-hook **משותף**, לא משוכפל: `src/features/<feature>/hooks/use-<name>.ts`
   ולא בתוך `team-list-web/`/`team-list-native/`. דוגמה: `src/features/teams/hooks/use-team-settings-panel.ts`,
   טיפוסים משותפים (`TeamCategory` וכו') ב-`src/features/teams/types.ts`.
4. הפיצול הזה הוא ברירת המחדל לכל קומפוננטה חדשה שמתקרבת ל-250 שורות, לא רק תיקון בדיעבד — אם
   ברור מראש שקומפוננטה תהיה מורכבת (טופס+רשימה+פילטר, למשל), התכננו את הפיצול הזה מהתחלה.
