# specs/

מסמכי אפיון מדויקים לפיצ'רים באפליקציה, נכתבים מתוך קריאה ישירה של הקוד (לא מהזיכרון ולא מהכוונה המקורית) — backend ו-frontend יחד באותו קובץ per feature, כדי שהם ישמשו מקור אמת יחיד לגזירת בדיקות בעתיד.

## איך להשתמש בקבצים האלה

כל קובץ בנוי לפי תבנית קבועה (ראה כל קובץ ספק לדוגמה מלאה). המיפוי בין סעיף לסוג בדיקה עתידי:

| סעיף | מה נגזר ממנו |
|---|---|
| §3 API Contract (טבלת error branches) | בדיקות unit ל-backend — כל שורה בטבלה = מקרה בדיקה אחד לפחות |
| §5 Client-Side Validation | בדיקות unit ל-frontend על הוולידציה |
| §6 UI States & Components | בדיקות unit ל-frontend על רינדור מצבים |
| §7 Cross-Cutting Flows | תרחישי e2e |
| §8 Edge Cases / Test Scenarios | רשימת המקרים שחייבים כיסוי — הבסיס לכתיבת קבצי הטסטים בפועל |
| §9 Known Discrepancies & Risks | מקרים שבהם הבדיקה צריכה להחליט: לבדוק את ההתנהגות בפועל (STATUS: Intentional) או לסמן כ-known-issue עד לתיקון (STATUS: Bug candidate) |

**חשוב:** הודעות שגיאה, ביטויי derivation, ושמות שדות בקבצים האלה מועתקים *מילה-במילה* מהקוד. אם הקוד משתנה, המסמך המתאים צריך להתעדכן יחד איתו — הוא לא תיאור-כוונה, הוא תיעוד-מציאות.

## קבצים קיימים

- [`00-shared-conventions.md`](./00-shared-conventions.md) — מוסכמות חוצות-תחום: auth, JWT, טיפול בשגיאות, דפוס קריאות API מה-frontend. שאר הקבצים מפנים לכאן במקום לחזור על זה.
- [`02-teams-and-approval.md`](./02-teams-and-approval.md) — יצירת צוות, תהליך האישור הדו-שלבי (approve/decline), ניהול חברים. **הכי מפורט מבחינת edge cases**, כי זה הפיצ'ר החדש ביותר וללא שום כיסוי בדיקות היום.
